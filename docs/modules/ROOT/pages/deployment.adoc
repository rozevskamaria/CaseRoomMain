= Deployment & Operations

== Production topology

Five containers on a single EU host (Hetzner), orchestrated with Docker Compose
(`deploy/docker-compose.prod.yml`):

[cols="1,3"]
|===
|Container |Role

|`caddy`
|TLS termination (automatic certificates), security headers, routing: `/graphql*` and `/sse/*` to the backend, everything else to the frontend. Also serves `api.caseroom.tech`.

|`frontend`
|nginx serving the built SPA (SPA fallback to `index.html`, no-store on the HTML shell).

|`backend`
|FastAPI under uvicorn with `--proxy-headers` (real client IPs for rate limiting). Not exposed to the host — reachable only through Caddy on the internal network.

|`worker`
|ARQ consumer for email delivery and research exports.

|`postgres` / `redis`
|Data stores. No host port mappings in production; internal network only.
|===

== Configuration

All configuration is environment-driven (`deploy/.env.prod.example` is the authoritative
template). The backend validates production configuration at startup and refuses to boot with
missing secrets — see xref:security.adoc[Security].

Key values: `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` (the model is configuration, and
changing it changes tutoring behaviour — a clinical decision, not an operational one),
`PGCRYPTO_KEY` and `LOGIN_HASH_PEPPER` (never rotate casually — the key decrypts existing
PII), `RESEND_API_KEY`/`RESEND_SENDER`, `PUBLIC_BASE_URL`, admin bootstrap logins, and the
optional MCP research settings.

== Database migrations

Schema changes ship exclusively as Alembic migrations (three to date: core persistence,
cohorts/assignments, research indexes). Apply with:

[source,bash]
----
cd backend && uv run alembic upgrade head
----

Migrations are applied before starting a new application version. Case content is seeded
idempotently (`app/db/seed.py`) — existing cases are never overwritten.

== Continuous integration

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request:

* Backend: ruff lint + full pytest suite.
* Frontend: eslint, `tsc` typecheck, vitest, production build.
* Docs: Antora site build.
* Compose file validation.
* **Changeset gate** (pull requests): the build fails if the PR does not include a changeset.
* **Deploy** (pushes to the default branch only, after every other job is green): builds this
  documentation site, syncs the repository and the built docs to the production host over
  SSH, rebuilds images, applies Alembic migrations, re-seeds cases idempotently, recreates
  the containers, and smoke-checks `https://api.caseroom.tech/health`. Server-only files
  (`deploy/.env`, local overrides) are excluded from the sync and protected from deletion.
  The job requires the `DEPLOY_SSH_KEY` / `DEPLOY_HOST` (and optional `DEPLOY_USER`)
  repository secrets and skips with a warning when they are absent.

== Accessing this documentation

* **Locally**: `npm run docs:build`, then open `build/site/index.html` or serve it
  (`python3 -m http.server -d build/site 8043`).

== Release flow (changesets)

The repository uses https://github.com/changesets/changesets[changesets] as its change log
mechanism. Every meaningful change lands with a `.changeset/*.md` file describing it and its
semver impact. On push to `main`, the release workflow
(`.github/workflows/release.yml`) aggregates pending changesets into a "Version packages"
pull request that bumps the version and writes `CHANGELOG.md`; merging it constitutes a
release. Day-to-day usage:

[source,bash]
----
npx changeset          # interactive: describe the change, pick a bump
npx changeset status   # what's pending
----

== Development environment

[source,bash]
----
cp .env.example .env       # add a real ANTHROPIC_API_KEY
docker compose up --build  # frontend :5173 · backend :8000 (GraphiQL enabled)
----

Development uses in-memory auth/attempt stores by default; `APP_ENV=production` switches to
the PostgreSQL/Redis-backed implementations. The database integration suite runs against a
disposable PostgreSQL on port 5433 (`pytest -m dbintegration`).
